# Versions

Each released version of **the standard** is frozen here under its full semver name: when the standard's version moves, `EIDOS.md` is copied in as-is (e.g. `v3.0.0.md`). The plugin versions separately and leaves no snapshot — see `CHANGELOG.md`. Because every release is preserved, any two (even non-adjacent) can be diffed to migrate a definition from one to another. See the `migrate` skill.

[`MIGRATIONS.md`](MIGRATIONS.md) beside them holds the worked hop for each release — what moves, what stays, and what needs a human decision. It is a shortcut, not a required path: `migrate` still diffs the two endpoints directly.

- `v1.0.0.md` — the original standard: `product/` root, the pre-2.0.0 frontmatter contract (`last_validated`, `implements`, `serves_job`, `activity`, `supersedes`) and the single `Behavior` / `Constraints` / `Decisions` body.
- `v2.0.0.md` — the breaking redesign: `Blueprint/` root, `created`/`modified`, `Behaviors & Acceptance Criteria` with `AC{n}`, merged `Constraints & Decisions`, `Dependencies` and `Testing`, and a default `Domains.md`.
- `v2.1.0.md` — adds the readability and reference-as-links conventions (including `depends_on` as links) and an `## AI` operating section.
- `v3.0.0.md` — the form-layer release: a registry owns its shapes and property contract in a hidden `.eidos/` (`shapes/`, `Schema.md`, `Registry.md`); property types from the Obsidian set; `eidos_version` retired in favour of `Registry.md`; frontmatter generated from the Schema; a new `eidos-property` skill; skills read the registry's form instead of vendoring templates.
- `v3.1.0.md` — additive: a per-registry naming convention (Title Case | TitleCase | kebab-case) recorded in `Registry.md` (now YAML frontmatter); the registry root located by its `.eidos/` marker, so it can take any name; and free-form top-level docs beyond the four, organized by `eidos-format` with no shape. The canonical property set is unchanged.
- `v4.0.0.md` — the big restructure. The Registry (`.eidos/Registry.md`) becomes the registry's **index** (Top-Level docs + Collections); `Specs` generalizes into declared **collections** with body **shapes** and **flavors** (`spec.full`/`spec.micro`, plus a `flavor` property), and the top-level `Domains.md` retires for a generated `index.md` per collection. **Top-level docs** move to one-of-each **templates** (`.eidos/templates/`), kept distinct from collection shapes. **Personas** (`.eidos/personas/`) plus a gitignored **`.eidos/user.md`** actor let the agent read who it's serving; a visible root `README.md` is the start-here; and `.gitignore` lives in `.eidos/`. New skills: `eidos-registry`, `eidos-index` (replacing `eidos-domains`), `eidos-whoami`.
- `v4.1.0.md` — navigation made mechanical and the framing docs generalized. Every item gains two optional properties, `summary` (the one-line index/reference blurb) and `connects_to` (canvas edges); the framing docs become an official **`Frames` collection** (the retired `templates/` become its flavor shapes); "top-level documents" become a purely user-created loose layer; `eidos-index` gains `build-index.py` and a new **`eidos-canvas`** skill ships; and the hidden form directory is renamed **`.eidos/` → `_eidos/`** so Obsidian shows it. Additive over 4.0.0.
- `v4.4.0.md` — the naming default flips: `kebab-case` is what the standard recommends and what an absent `naming` key now means, where it used to mean `Title Case`. A definition that carries the key is unaffected; one that doesn't should have its convention read off its own files and written down. The canvas's default filename now follows the convention too (`framework-map.canvas`), and `README.md` is named as an exception alongside `_eidos/`. Also renames `_eidos/personas/` → `_eidos/roles/` and `_eidos/user.md` → `_eidos/me.md` (both borrowed words that already meant something else in a product definition; the concept stays **actor**), and has the agent check a definition's `eidos_version` against its own once per session.
- `v4.3.2.md` — splits the plugin's version from the standard's; the only text change is the Versioning section. From here a skill fix bumps the plugin and leaves this file alone.
- `v4.3.1.md` — a tooling release; the standard text is identical to 4.3.0. Worked migrations move to `MIGRATIONS.md`, the skills shrink 25%, and several places where they still named the software seed's sections are fixed.
- `v4.3.0.md` — the de-biasing release: `EIDOS.md` stops naming any collection, shape, or section, and every example in it becomes a placeholder. Six Rules generalize or fold into the shape files; a collection declares how it draws on the canvas (`- **Canvas:**`); every framework must now declare a framing collection; `build-canvas.py` no longer special-cases `Frames` or `## Intent`. Ships `seeds/` (software, book, research) in place of the single `seed/`, and a second worked example. Additive per definition: declare Canvas, bump the version.
- `v4.2.1.md` — the vocabulary fix: a **framework** is the `_eidos/` form layer (collections, shapes, flavors, personas, naming, Schema), and a **definition** is the product written with it. Prose only — no file, folder, or property changes; migration is a one-line `eidos_version` bump.
- `v4.2.0.md` — the earlier vocabulary release: the per-product artifact becomes a **Framework** (not a "registry"). `_eidos/Registry.md` → `_eidos/Framework.md`; the `registry-owner` persona → `framework-owner`; the generated "Registry Map" → "Framework Map". The `eidos-registry` and `eidos-schema` skills merge into **`eidos-configure`**. Mechanical file renames, fully migratable; no item or behavior changes.

The current version always lives in the top-level `EIDOS.md` (identical to the latest snapshot here until work on the next version begins). See `CHANGELOG.md` for history and migrations.
