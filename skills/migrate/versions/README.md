# Versions

Each released version of **the standard** is frozen here under its full semver name: when the standard's version moves, `EIDOS.md` is copied in as-is (e.g. `v3.0.0.md`). The plugin versions separately and leaves no snapshot — see `CHANGELOG.md`. Because every release is preserved, any two (even non-adjacent) can be diffed to migrate an Eidos folder from one to another. See the `migrate` skill.

[`MIGRATIONS.md`](MIGRATIONS.md) beside them holds the worked hop for each release — what moves, what stays, and what needs a human decision. It is a shortcut, not a required path: `migrate` still diffs the two endpoints directly.

- `v1.0.0.md` — the original standard: `product/` root, the pre-2.0.0 frontmatter contract (`last_validated`, `implements`, `serves_job`, `activity`, `supersedes`) and the single `Behavior` / `Constraints` / `Decisions` body.
- `v2.0.0.md` — the breaking redesign: `Blueprint/` root, `created`/`modified`, `Behaviors & Acceptance Criteria` with `AC{n}`, merged `Constraints & Decisions`, `Dependencies` and `Testing`, and a default `Domains.md`.
- `v2.1.0.md` — adds the readability and reference-as-links conventions (including `depends_on` as links) and an `## AI` operating section.
- `v3.0.0.md` — the form-layer release: a registry owns its shapes and property contract in a hidden `.eidos/` (`shapes/`, `Schema.md`, `Registry.md`); property types from the Obsidian set; `eidos_version` retired in favour of `Registry.md`; frontmatter generated from the Schema; a new `eidos-property` skill; skills read the registry's form instead of vendoring templates.
- `v3.1.0.md` — additive: a per-registry naming convention (Title Case | TitleCase | kebab-case) recorded in `Registry.md` (now YAML frontmatter); the registry root located by its `.eidos/` marker, so it can take any name; and free-form top-level docs beyond the four, organized by `eidos-format` with no shape. The canonical property set is unchanged.
- `v4.0.0.md` — the big restructure. The Registry (`.eidos/Registry.md`) becomes the registry's **index** (Top-Level docs + Collections); `Specs` generalizes into declared **collections** with body **shapes** and **flavors** (`spec.full`/`spec.micro`, plus a `flavor` property), and the top-level `Domains.md` retires for a generated `index.md` per collection. **Top-level docs** move to one-of-each **templates** (`.eidos/templates/`), kept distinct from collection shapes. **Personas** (`.eidos/personas/`) plus a gitignored **`.eidos/user.md`** actor let the agent read who it's serving; a visible root `README.md` is the start-here; and `.gitignore` lives in `.eidos/`. New skills: `eidos-registry`, `eidos-index` (replacing `eidos-domains`), `eidos-whoami`.
- `v4.1.0.md` — navigation made mechanical and the framing docs generalized. Every item gains two optional properties, `summary` (the one-line index/reference blurb) and `connects_to` (canvas edges); the framing docs become an official **`Frames` collection** (the retired `templates/` become its flavor shapes); "top-level documents" become a purely user-created loose layer; `eidos-index` gains `build-index.py` and a new **`eidos-canvas`** skill ships; and the hidden form directory is renamed **`.eidos/` → `_eidos/`** so Obsidian shows it. Additive over 4.0.0.
- `v5.1.0.md` — regions: a tool keeps what it needs inside a markdown file between two HTML comments carrying its name, `<!-- <tool>:<region> <args> -->` to `<!-- /<tool>:<region> -->`, the same identifier as its `plugins/` folder and Properties block; the contents are the tool's own, rewritten wholesale, never read or faulted by the standard, and a parser skips fenced code and accepts both closers HTML allows. Also adds `required` to a property entry (absent = `false`): frontmatter is generated from the required properties, a missing one is surfaced, and an optional one is written when it has a value and never a gap; the core's `id` and `title` are required. Additive; migration is a one-line `eidos_version` bump, and the core block is rewritten as always.
- `v5.0.0.md` — the vocabulary release: `Schema` is **Properties**, `shape` is **template**, `flavor` is **variant** (a core property, so it moves on every blueprint), and `_eidos/` is **`.eidos/`** again; the term table is reordered by hierarchy and rewritten in plain words, `unit` is declared and `term` and `actor` fold away, a template file is `<unit>.<variant>.md` and carries no frontmatter, both faulted; and the framework document has one form, `Framework.yaml`, the markdown `Framework.md` and the per-collection `index.md` leaves leaving with it (the index lives under `index`). Breaking: keys, a folder, a property, filenames, and the document's form move, all mechanically; the hop is one rename pass, a conversion for a markdown root, and a version bump.
- `v4.7.0.md` — ownership by block: every Schema property is owned by the block it sits in, and a tool that declares properties of its own gets `### <tool> Properties` (`schema.tools.<tool>`) beside `### Eidos Core` and `### Custom Properties`, written by that tool alone. Eidos is the first tool. `id` loses its kebab-case requirement (stable and unique, any form), and `connects_to` leaves the core (the four are `id`, `title`, `summary`, `flavor`; relationships belong in the body as links), as does the collection's `Canvas` bullet: a view a tool draws is that tool's. Additive; migration is a one-line `eidos_version` bump.
- `v4.6.0.md` — the terms release: **product** becomes a declared term for what a root defines (the standard stops saying "the thing"); a framework declares its **Vocabulary** beside its Schema, one row per term the root uses on purpose (**Term · Means · Not**), as a `## Vocabulary` section in `Framework.md` or a `vocabulary` key in `Framework.yaml`. `term` and `Vocabulary` join the standard's own table, and Rule 20 (a declared term is the word) is appended without renumbering. Also lets a root be snapshotted as a version, on purpose and only when asked (`## Versions`: **Version · Commit · Tag**, a named commit with an optional `blueprints/<version>` tag, nothing copied, never a blueprint property, empty until a team wants a fixed point; Rule 15 grows to say so), and opens `_eidos/` to tools the way `.obsidian/` is: `_eidos/plugins/<name>/` is a tool's own folder, and a Schema row may carry a tool's fields past the standard's four. Additive: every seed ships the section empty, Eidos declares no term of a framework's, and migration is a one-line `eidos_version` bump plus the empty section.
- `v4.5.0.md` — the framework document gains a second form: **`Framework.yaml`**, the same fields as data, for a root that scripts and agents read; it keeps every collection's index inside the document instead of in per-collection `index.md` files. `Framework.md` stays the form for people. The standard ships no canvas generator any more (the declarations stay), and "prefer the skills" becomes "prefer the tooling": the `eidos` command does the mechanical part. Additive: every existing root conforms as it stands; migration is a one-line `eidos_version` bump.
- `v4.4.3.md` — the one-word fix: a **framework** is the *structure* a root is written in, not the *form*, since "form" and "shape" read as synonyms and `shape` is a term in the same table. "The form layer" becomes "the structure layer" throughout, and the file's opening line says "the terms, the layout, and the rules". The Greek gloss keeps "form": that line is etymology. Prose only; migration is a one-line `eidos_version` bump.
- `v4.4.2.md` — the clarity pass: **root** becomes a declared term for the one folder Eidos lives in (4.4.1 retired "definition" and left the concept unnamed); `shape` and `flavor` stop defining each other; `frame` drops "point-in-time", which read as expiry beside a standard about timeless blueprints; the Rules go 24 → 19 as five restatements fold back into the sections that already carried them, and renumber; and the generated canvas becomes the **Blueprint Map** (`blueprint-map.canvas`), since the framework is the one thing it never draws. Prose only — migration is a one-line `eidos_version` bump.
- `v4.4.1.md` — the vocabulary release: an **item** becomes a **blueprint**, and **definition** is retired with nothing in its place, so Eidos turns on two words, framework and blueprint. The default root name goes plural (`Blueprints/`), though an existing root keeps its name and needs no rename. Prose only — no file, folder, or property changes; migration is a one-line `eidos_version` bump.
- `v4.4.0.md` — the naming default flips: `kebab-case` is what the standard recommends and what an absent `naming` key now means, where it used to mean `Title Case`. A definition that carries the key is unaffected; one that doesn't should have its convention read off its own files and written down. The canvas's default filename now follows the convention too (`framework-map.canvas`), and `README.md` is named as an exception alongside `_eidos/`. Also renames `_eidos/personas/` → `_eidos/roles/` and `_eidos/user.md` → `_eidos/me.md` (both borrowed words that already meant something else in a product definition; the concept stays **actor**), and has the agent check a definition's `eidos_version` against its own once per session.
- `v4.3.2.md` — splits the plugin's version from the standard's; the only text change is the Versioning section. From here a skill fix bumps the plugin and leaves this file alone.
- `v4.3.1.md` — a tooling release; the standard text is identical to 4.3.0. Worked migrations move to `MIGRATIONS.md`, the skills shrink 25%, and several places where they still named the software seed's sections are fixed.
- `v4.3.0.md` — the de-biasing release: `EIDOS.md` stops naming any collection, shape, or section, and every example in it becomes a placeholder. Six Rules generalize or fold into the shape files; a collection declares how it draws on the canvas (`- **Canvas:**`); every framework must now declare a framing collection; `build-canvas.py` no longer special-cases `Frames` or `## Intent`. Ships `seeds/` (software, book, research) in place of the single `seed/`, and a second worked example. Additive per definition: declare Canvas, bump the version.
- `v4.2.1.md` — the vocabulary fix: a **framework** is the `_eidos/` form layer (collections, shapes, flavors, personas, naming, Schema), and a **definition** is the product written with it. Prose only — no file, folder, or property changes; migration is a one-line `eidos_version` bump.
- `v4.2.0.md` — the earlier vocabulary release: the per-product artifact becomes a **Framework** (not a "registry"). `_eidos/Registry.md` → `_eidos/Framework.md`; the `registry-owner` persona → `framework-owner`; the generated "Registry Map" → "Framework Map". The `eidos-registry` and `eidos-schema` skills merge into **`eidos-configure`**. Mechanical file renames, fully migratable; no item or behavior changes.

The current version always lives in the top-level `EIDOS.md` (identical to the latest snapshot here until work on the next version begins). See `CHANGELOG.md` for history and migrations.
